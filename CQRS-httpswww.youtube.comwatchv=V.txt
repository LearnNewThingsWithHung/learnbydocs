Command Query Responsibility Segregation

Comand: ghi -> thay đổi dữ liệu
Query: đọc -> lấy dữ liệu
Seperation: tách biệt

=> Kiến trúc giúp tách biệt phần đọc với phần ghi

- Đọc: thì giúp cho đọc nhanh hơn -> nó ưu tiên tốc độ
- Ghi: thì nó ưu tiên tính toán viện hơn
- Và nó tách biệt: nên 2 thằng sẽ phải liên kết với nhau (***)

-> Đây là kiến trúc 3 lớp kinh điển(monolith), và trong quá trình phát triển thì kiến trúc lại mang lại nhiều nhược điểm:

+Khi việc đọc ghi liên tục diễn ra liên tục cùng một lúc, nhiều lên thì dẫn đến bị nghẽn db(bottel neck) do các luồng request tranh chấp tài nguyên của cùng database -> làm giảm hiệu năng của hệ thống

+Khó mở rộng độc lập: khi nhu cầu đọc tăng đột biến, phải mở rộng cả phần xử lí đọc và ghi dù phần ghi là chưa cần thiết -> lãng phí tài nguyên

Vậy khi dùng CQRS chỉ để tách biệt thôi, vậy khi đã tách biệt rồi thì việc chúng giao tiếp với nhau để đảm bảo đồng bộ dữ liệu còn là một vấn đề khác nữa

Vì vậy mà mình hay thấy rằng người ta hay dùng combo đó là: CQRS + MediatR (tách bạch + giao tiếp)

### PHÂN BIỆT

1. Với kiến trúc 3-tier thông thường

Cả đọc và ghi đều đi qua cùng Business Logic và thường dùng chung Model, Database.

Ví dụ:

• Request A: Đặt hàng → ghi dữ liệu.
• Request B: Xem danh sách đơn hàng → đọc dữ liệu.

Hai request có thể diễn ra cùng lúc, nhưng phải chia sẻ tài nguyên xử lý chung. Khi lượng request lớn, chúng có thể cạnh tranh tài nguyên.


2. Với CQRS

CQRS chia thành hai luồng xử lý riêng:

┌─────────────────────────────────────────────│                                                              │
│                    Command — Ghi dữ liệu                     │
│                                                              │
│         Đặt hàng → Xử lý nghiệp vụ → Write Model → DB        │
│                                                              │
├─────────────────────────────────────────────┤
│                                                              │
│                     Query — Đọc dữ liệu                      │
│                                                              │
│                 Xem đơn hàng → Read Model → DB               │
│                                                              │
└─────────────────────────────────────────────┘

Hai luồng có thể được tối ưu và mở rộng độc lập.

Ví dụ, website có 1.000 request xem sản phẩm nhưng chỉ 20 request cập nhật sản phẩm. CQRS cho phép mở rộng phần đọc nhiều hơn mà không cần mở rộng tương ứng phần ghi.
